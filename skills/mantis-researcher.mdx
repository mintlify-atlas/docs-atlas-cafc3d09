The `/mantis-researcher` skill consumes `workspace/plan.json` and performs thorough static analysis of the targeted source files. It operates in two waves: a lightweight concurrent triage sweep (Wave 1) followed by deep-dive audits of flagged hotspots (Wave 2). Every finding is written as an individual `workspace/findings/<uuid>.json` file with a deterministic content-identity signature and cross-pass lineage ID. Use it when a review plan exists and you need static analysis and deep-dive audits of targeted files. Do not use it for planning, deduplicating findings, or writing patches.

## Command

```bash
/mantis-researcher [--snapshot_root <dir>] [--snapshot_id <id>]
                   [--state_root <dir>] [--target_root <dir>]
```

<ParamField path="--snapshot_root" type="string" optional>
  Absolute path to the pinned, read-only code snapshot. All `target_files` and `code_paths` in plan and findings are resolved under this directory.
</ParamField>

<ParamField path="--snapshot_id" type="string" optional>
  The pass snapshot identifier. Stamped verbatim as `discovery_commit` into every finding created this pass. Required when the snapshot is pinned — omitting it causes downstream Block B to treat findings as NOT_MATCHED.
</ParamField>

<ParamField path="--state_root" type="string" optional>
  Parent directory of `workspace/`. `plan.json`, `.mantis_state.json`, `kb_references`, and all `workspace/findings/` files are STATE-RELATIVE — never prefixed with `CODE_ROOT`. When absent, defaults to `./workspace/` (DEGRADED/legacy mode).
</ParamField>

<ParamField path="--target_root" type="string" optional>
  Authoritative override for `CODE_ROOT`. Used when a caller passes a prepared tree (e.g., a patched shadow copy). Overrides `--snapshot_root` and the state fallback.
</ParamField>

<Note>
  **All flags absent → DEGRADED/legacy mode.** `CODE_ROOT` falls back to the current directory, `snapshot_pinned` is treated as false, and `discovery_commit` is omitted from findings. All other behavior matches today's pipeline exactly.
</Note>

## Input / Output Contract

### Reads

| Path | Purpose |
|------|---------|
| `workspace/plan.json` | Investigation roadmap (falls back to general codebase sweep if missing) |
| `workspace/.mantis_state.json` | Pass number, timestamp, and `active_snapshot` |
| `workspace/kb/entities/*.md`, `workspace/kb/vulnerabilities/*.md` | KB context files listed in each investigation's `kb_references` |
| `CODE_ROOT` target source files | The actual code being audited |
| `workspace/kb/structural_index/manifest.json` | Structural index availability/status |
| `workspace/helpers/query_structural_index.py` | Bounded structural index queries |

### Writes

| Path | Content |
|------|---------|
| `workspace/findings/<uuid>.json` | One file per finding — structured JSON with signature and lineage |

## Two-Wave Execution

<Steps>
  <Step title="Wave 1: Lightweight Rapid Triage">
    Spawn up to 10–20 concurrent lightweight sub-agents to sweep all files listed in `workspace/plan.json`. Each sub-agent outputs a fast classification:

    ```json
    {"potentially_flawed": true, "reason": "Unchecked return value from malloc before pointer dereference at line 87"}
    ```

    Sub-agents use the structural index (if available) to rank candidate call-sites — but grep remains the mandatory floor. All sub-agents receive the same `--snapshot_root` and `--snapshot_id` and must not modify the working tree.
  </Step>
  <Step title="Wave 2: Deep Security Audit">
    Collect all files flagged in Wave 1. Spawn up to 4–8 concurrent deep auditor sub-agents to focus exclusively on identified hotspots. For particularly complex files, multiple sub-agents may target the same file using different prompt constraints or diverse LLM tiers to explore parallel attack vectors.

    Wave 2 sub-agents write findings directly to `workspace/findings/<uuid>.json` and return only the list of UUIDs created — never the full JSON payload — to avoid blowing out the orchestrator's context window.
  </Step>
</Steps>

## Finding Schema

Each finding is written as a standalone JSON file at `workspace/findings/<uuid>.json`:

```json
{
  "id": "<uuid>",
  "title": "Buffer overflow in parse_input() via unchecked length",
  "description": "Root cause analysis detailing why the function is flawed under untrusted input.",
  "impact": "Memory corruption leading to arbitrary code execution",
  "severity": "CRITICAL",
  "privileges_required": "NONE",
  "attacker_position": "EXTERNAL",
  "user_interaction": "NONE",
  "status": "PROVISIONALLY_VALID",
  "code_paths": ["src/parser.c:87"],
  "discovery_commit": "<active_snapshot.snapshot_id>",
  "cwe": "CWE-787",
  "signature": "a1b2c3d4e5f67890",
  "lineage_id": "<uuid-v4 or inherited>",
  "mitigation": "Add bounds check before memcpy: if (len > sizeof(buf)) return -1;",
  "history": [
    {
      "stage": "researcher",
      "action": "created",
      "details": "Initial audit finding recorded.",
      "pass_number": 1,
      "timestamp": "2024-01-15T10:30:00Z"
    }
  ]
}
```

## Signature and Lineage Computation

Every finding has a deterministic content-identity signature and a cross-pass lineage ID, computed once at creation and never recomputed:

<Tabs>
  <Tab title="Signature">
    ```python
    normalized_title = re.sub(r'[^a-zA-Z0-9]', '', title.lower())
    # If stripping leaves empty string, use first 16 hex chars of sha256(raw title)
    cwe_part = cwe if cwe else ""
    primary_target = code_paths[0].rsplit(":", 1)[0]  # strip trailing :line

    signature = sha256(
        normalized_title + "|" + cwe_part + "|" + primary_target
    ).hexdigest()[:16]
    ```

    The signature is stable across passes as long as the title, CWE, and primary file path remain the same. It is used by `/mantis-plan` (Block B snapshot match) and `/mantis-dedupe` for cross-pass folding.
  </Tab>
  <Tab title="Lineage ID">
    The researcher scans `workspace/archive/findings_pass_*/` and `workspace/archive/loop*_findings/` for any archived finding whose `signature` matches:

    - **Exact match found:** inherit the ancestor's `lineage_id` (chain the lineage). If multiple match, inherit from the most recent pass.
    - **No exact match, but basename rename:** inherit from an ancestor whose `code_paths[0]` basename matches AND whose old full path no longer exists under `CODE_ROOT`. Add a `lineage-via-basename-rename` history note.
    - **No match:** `lineage_id` = a fresh UUIDv4.

    `lineage_id` is **always** computed, even in DEGRADED/legacy mode (unlike `discovery_commit` which is omitted when unpinned).
  </Tab>
</Tabs>

## Usage

### Standalone invocation (DEGRADED mode)

```bash
/mantis-researcher
```

### With snapshot and state root (orchestrated)

```bash
/mantis-researcher \
  --snapshot_root /tmp/mantis/snapshots/snap_abc \
  --snapshot_id snap_abc \
  --state_root /tmp/mantis/state
```

## Notes

<Accordion title="Snapshot isolation (wave pinning)">
  All Wave-1 and Wave-2 sub-agents receive the **same** `--snapshot_root` and `--snapshot_id`. Sub-agents must:

  - Resolve `target_files` and `code_paths` under `CODE_ROOT`
  - Honor the snapshot sentinel check
  - Write `discovery_commit` = `SNAPSHOT_ID` in every finding
  - **Never** run `git pull`, `git checkout`, `git reset`, `hg pull`, `hg update`, `repo sync`, or any command that changes the working tree or switches revisions

  A sub-agent that cannot see the snapshot must report that, not re-sync.
</Accordion>

<Accordion title="Exhaustive call-site review">
  For target files that define public or API functions with documented size constraints or safety requirements, the researcher performs a **repo-wide grep** for the function name to build the exhaustive set of candidate call-sites. This is the mandatory floor.

  The structural index query helper (`resolve_symbol` + `find_callers`) is then used to **rank and prioritize** which call-sites to audit first — distinguishing actual calls from comments, strings, and variable names. The researcher audits the **union** of grep and structural index results. The structural index may miss macro-based calls, function pointers, and dynamic dispatch, so grep is never replaced.
</Accordion>

<Accordion title="Structural index usage (HINT-only)">
  When `workspace/kb/structural_index/manifest.json` exists:

  - **Wave 1:** Use `find_callers()` to supplement grep as a ranking hint — ORDER, never MEMBERSHIP.
  - **Wave 2:** Use `get_function_boundary(file, line)` to start with the enclosing function, then expand to callers/callees/file as needed.
  - **Resolution-first:** Always call `resolve_symbol()` before `find_callers()`. If `ambiguous: true`, investigate ALL matched symbols — never silently pick one.
  - **Coverage-aware:** If `partition_status` is `partial`, `empty`, or `failed`, run exhaustive grep — the partition is not fully indexed.

  If the structural index is absent or empty, fall back to grep-only discovery (today's exact behavior).
</Accordion>

<Accordion title="Missing or unreadable target files">
  If a path in `target_files` does not exist or cannot be read under `CODE_ROOT` (e.g., deleted or renamed since the plan was written), the researcher **does not fabricate** a finding, line number, or file content. The target is skipped and the skip is recorded plainly in the description of any related finding (or omitted entirely). Never invent code you did not read.
</Accordion>

<Accordion title="Unconstrained / exploratory investigations">
  When `workspace/plan.json` contains an investigation asking for an unconstrained sweep, adversarial audit, or random exploration:

  - Ignore existing safety assumptions and documented trust boundaries in `THREAT_MODEL.md`
  - Treat all inputs and boundaries as untrusted and potentially malformed
  - Analyze the implementation from scratch with full autonomy
  - For minimal open-ended tasks ("dig into this directory"), focus on mapping behavior, identifying key entry points, and looking for unexpected side effects without constraint
</Accordion>
