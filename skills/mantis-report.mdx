The `/mantis-report` skill synthesizes the complete output of a Mantis campaign into a professional, stakeholder-ready security review packet. It reads every active finding from the current pass alongside carried-forward open findings from all prior passes, applies campaign-wide deduplication, and writes a structured Markdown report with executive summary tables, reproduction evidence, patch diffs, and risk rationale. Use this skill at the end of a review cycle, after calibrate has appended risk scores. Do not use it to audit code, run exploits, or verify patches — it is a **findings-only** stage that reads no target source code.

## Command

```text
/mantis-report
```

No positional arguments. All inputs are resolved from `workspace/findings/`, `workspace/archive/`, and `workspace/.mantis_state.json`.

## Input / Output Contract

**Reads:**

| Path | Purpose |
|---|---|
| `workspace/findings/*.json` | All active finding files for this pass |
| `workspace/archive/findings_pass_*/*.json` | Archived findings from prior passes (for carried-forward open findings) |
| `workspace/archive/loop*_findings/*.json` | Legacy archive format |
| `workspace/.mantis_state.json` | `pass_number`, `vcs_info`, `active_snapshot` for provenance and output filename |
| `workspace/archive/.repro_attempts.json` | Per-finding retry counts for the "retry cap reached" callout (optional) |

**Writes:**

| Path | Description |
|---|---|
| `workspace/report/review_packet_pass_<N>_<snapshot_tag>.md` | Pass- and snapshot-tagged report (when `active_snapshot.snapshot_id` is present) |
| `workspace/report/review_packet_pass_<N>.md` | Legacy unsuffixed name (when no snapshot is recorded) |
| `workspace/report/review_packet-latest.md` | Always-updated copy/symlink pointing to the latest report |

**Preconditions:** Calibrated and reproduced findings must exist in `workspace/findings/` or `workspace/archive/`. The report is a campaign-wide view — it includes findings from all passes, not just the current one.

**Idempotency:** Re-running on the same pass and snapshot overwrites the same `<snapshot_tag>`-suffixed file. Running the same pass number on a different snapshot writes a **distinct** file (the snapshot suffix prevents cross-snapshot overwrite). The `review_packet-latest.md` symlink/copy is always updated.

## Finding Inclusion Rules

Reporter applies a strict **actionable / quality predicate** to determine which findings appear in the main report body:

Include a finding only if **one** of the following is true:
1. It is an exploit chain (`constituent_findings` present, or `"Exploit Chain"` in title/history).
2. `repro_status` is `reproduced`.
3. `repro_status` is `statically_confirmed` **AND** the finding carries empirical execution evidence — an external stack trace, sanitizer trace (ASan/UBSan/MSan/TSan), or crash log.

**Always exclude:** `FALSE_POSITIVE`, `NON_VIABLE`, `DUPLICATE`, `failed_to_reproduce`, or `statically_confirmed` findings lacking empirical traces.

**LOW priority findings** are excluded from the main report body and placed in a dedicated **"Appendix: Low Priority Findings"** section at the end.

## Report Structure

<Steps>
  <Step title="Snapshot provenance banners">
    Before the executive summary, the reporter emits up to three blockquote banners:

    1. **Non-authoritative / HALT warning** — emitted only when `active_snapshot` is present but `snapshot_pinned` is `false` (HALT mode). Not emitted in MODE-OFF.
    2. **Dirty working tree warning** — emitted when `vcs_info.dirty` is `true`.
    3. **Mixed snapshots warning** — emitted when the report includes findings from multiple different `discovery_commit` values.
  </Step>
  <Step title="Target version and disclaimer">
    Reports the VCS state (`git branch/commit`, `hg branch/revision`, `multi-vcs manifest`, or `none`) read from `vcs_info`, plus the `Snapshot ID` line from `active_snapshot`.

    Includes a mandatory disclaimer: *"This report was automatically generated by Mantis AI. All findings and patches are AI-generated and must be manually verified by a security or subject matter expert before deployment or disclosure."*
  </Step>
  <Step title="Executive Summary table">
    A high-level table listing all included findings with their priority, risk score, and patch status.
  </Step>
  <Step title="Findings grouped by patch status">
    Standard (non-chain) findings appear in exactly three mutually exclusive categories:

    - **Category 1: Patch Independently Verified** — `patch_status: VERIFIED_SECURE`
    - **Category 2: Patch Proposed / Mitigation Identified** — `patch_status` in `[MITIGATION_PROPOSED, VERIFICATION_INCOMPLETE]`, or `patch_diff` present with no status
    - **Category 3: Unpatched / Verification Failed** — `patch_status` in `[VERIFICATION_FAILED, ERROR]`, or no `patch_diff` and no status
  </Step>
  <Step title="Exploit Chains section">
    A dedicated **"Exploit Chains (Not End-to-End Reproduced)"** section lists each chain with its title, risk score, and constituent findings. Chains are never mixed into Categories 1–3.
  </Step>
  <Step title="Optional sections">
    - **Resolved this campaign** — findings where `patch_status` is `VERIFIED_SECURE` or `MITIGATION_PROPOSED`
    - **Unresolved — retry cap reached** — open findings whose retry count in `.repro_attempts.json` is at the cap
    - **Appendix: Low Priority Findings** — all `LOW` priority findings excluded from the main body
  </Step>
</Steps>

## Per-Finding Content

For each included finding, the report renders:

<Accordion title="Header metadata">
Title, UUID, Inferred Exposure, Final Risk Score, Qualitative Priority, and campaign provenance (e.g., `discovered pass 2 · still open as of pass 7`).

If the finding has a `possible_duplicate_of` field (set by `mantis-dedupe` when a cross-pass candidate was NOT_MATCHED), emit an advisory note: *"Possibly related to finding `<UUID>` (cross-pass candidate; snapshots differ — not confirmed duplicate)."*
</Accordion>

<Accordion title="Snapshot provenance fields">
- **Discovery Snapshot:** `discovery_commit` value, or `"(legacy — not recorded)"` if absent.
- **Evidence base:** `repro_snapshot_id` value, or `"(not recorded)"` if absent. Never assumed to equal the pass snapshot.
- **Apply against:** `patch_base_snapshot` value, or `"(not recorded)"` if absent. If `patch_base_snapshot` differs from `discovery_commit`, a caution is added that the diff may not apply cleanly.
</Accordion>

<Accordion title="Vulnerability description and reproduction evidence">
- Clear explanation of the bug and concrete impact.
- PoC script path (`repro_file_path`) and execution command (`run_command`).
- Clean stdout/stderr snippet showing the successful exploit trigger (`repro_output`).
</Accordion>

<Accordion title="Risk rationale">
Independent validation reasoning (`reasoning`), production viability reasoning (`critic_reasoning`), and outrage factor analysis (`outrage_commentary`).
</Accordion>

<Accordion title="Remediation and patch">
Recommended mitigation strategy, verified patch diff (`patch_diff`), and re-attack bypass status.
</Accordion>

## PII and Secrets Redaction

Before writing any finding data to the report, the skill scans and redacts:

- Hardcoded API keys, tokens, credentials
- PII (names, emails, phone numbers)
- Internal hostnames and domain names
- Overly weaponized payload parameters

Replacements use standard placeholders: `<REDACTED_SECRET>`, `<REDACTED_PII>`, `<REDACTED_INTERNAL_HOST>`, `<REDACTED_PAYLOAD>`.

## Deduplication Predicate

Two findings are treated as the **same bug** only when **either**:
1. They share the exact same `id` (UUID), **or**
2. ALL THREE hold: shared non-empty `lineage_id` + shared non-empty `signature` + at least one line-inclusive `code_paths` entry is identical.

Matching on `lineage_id` alone or `signature` alone is **explicitly forbidden** — basename-derived lineage can link distinct files, and a `signature` strips line numbers so it collides between distinct same-file bugs. When in doubt, the reporter over-reports rather than hides.

<Warning>
**Under-reporting safeguard:** If the current (superseding) finding fails the actionable predicate — for example, reproduction returned `not_attempted` due to a transient build failure on a new snapshot — but the archived ancestor was confirmed and open, the ancestor's last confirmed state remains visible in the report with a note: *"Open — repro pending on new snapshot."* A previously-confirmed bug can never silently disappear from the report.
</Warning>

## Output Filename Convention

The output filename encodes both the pass number and the snapshot identity:

```text
workspace/report/review_packet_pass_<N>_<snapshot_tag>.md
```

`<snapshot_tag>` is the `active_snapshot.snapshot_id` with every character outside `[A-Za-z0-9.-]` replaced by `_`. The full ID is used without truncation.

When no snapshot is recorded (legacy runs or MODE-OFF without an explicit `active_snapshot`), the unsuffixed legacy name is used:

```text
workspace/report/review_packet_pass_<N>.md
```

The `review_packet-latest.md` symlink/copy is always updated and is the **authoritative current open state** of the whole campaign.

## Usage

Report is invoked by the meta-agent as **Stage 14**, after Reflect:

```text
/mantis-report
```

With snapshot pinning active:

```text
/mantis-report --snapshot_root=<active_snapshot.root> --snapshot_id=<active_snapshot.snapshot_id> --state_root=<workspace parent>
```

## Notes

<Note>
**Campaign-wide view:** The report is not limited to the current pass. It includes carried-forward open findings from all prior passes that have not yet been resolved — a finding confirmed in pass 2 still appears in the pass 7 report unless it has been patched and verified.
</Note>

<Note>
**Pass number resolution:** The pass number `N` is read from `pass_number` in `workspace/.mantis_state.json`. If missing or invalid, the skill scans `workspace/archive/` for `findings_pass_N` or `loopN_findings` folders and resolves `N = max_found + 1`, defaulting to 1 if no archives exist.
</Note>

<Tip>
The `review_packet-latest.md` file is the stable entry point for any downstream consumer (bug tracker integrations, CI/CD gates, stakeholder dashboards). It always reflects the most recent report regardless of pass number or snapshot suffix.
</Tip>
